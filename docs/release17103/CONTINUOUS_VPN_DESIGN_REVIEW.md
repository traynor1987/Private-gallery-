# Critical C1 continuous VPN design review

Reviewed 2026-11-03, branch release/1.7.10-private-home, design baseline e772b50a8927df0a2976428487c4d4f9826cb233. Read-only review of CONTINUOUS_VPN_DESIGN.md, CONTINUOUS_VPN_PLAN.md, CONTINUITY_SECURITY_REVIEW.md, pinned native/Java snapshots, and current broker, session, DNS and readiness code. No repository edits, builds, CI, signing, or approval changes.

## Scoped verdict

**Feasible enough to begin a native gate and host-tested integration. Conditional implementation direction, not release/security approval.** A continuously retained full-route Android TUN, per-transport native plaintext/outer-send gates, and fresh WG devices can repair the demonstrated app-controlled route-removal failure without replacing the browser or sacrificing ordinary connected UDP. The implementation must resolve the concrete obligations below; merely retaining a duplicate FD and wrapping Read is insufficient.

Full capture assertions and native child probes must remain. Same-Network identity is an intentional architectural change, so replace Network inequality with positive persistent-fence identity plus fresh transport-generation, protection, handshake and readiness receipts. Do not relax the no-fallback rule or its time window.

## 1. Minimum native state machine and concurrency contract

Use a lifetime fence identity independent of a transport generation. Each transport has an unforgeable native handle, monotonic generation, phase, protection status and revocation sequence. Do not reuse integer handles in a way that lets a stale caller target another transport. The upstream global tunnelHandles map is unsynchronized and cannot simply be copied into a concurrently called JNI surface.

A safe simple transition graph is fresh CLOSED -> PROBE -> OPEN, with any suspension/revocation/failure permanently closing that generation. Retire it and create a different device/gate before probing again. A close acknowledgement includes fence identity, generation and revocation sequence, and is emitted only when all already admitted outer sends and plaintext TUN writes have finished or have been cancelled by closing that transport's socket/TUN duplicate. CLOSED is the constructor and exception default. A deadline failure must leave the generation unusable and the original TUN retained; never acknowledge successful denial while a write is still pending.

The send gate must wrap the actual conn.Bind.Send implementation, including handshake/cookie traffic. The pin sends cookies directly through device.net.bind.Send, bypassing Peer.SendBuffer; hooking only Peer.SendBuffer misses this path. A mutex/active-operation barrier needs a specified linearization point: mark closed first, reject new entrants, then wait for existing entrants. Do not hold it across blocking TUN Read. Do not hold it while calling a close path that needs the same lock. Closing the old transport's sockets and duplicate can unblock stuck I/O while the separately retained original keeps the route alive.

Plaintext Read and Write require separate policy checks. A dropped Read must consume/drop and continue or return a successful zero-length read; the pinned reader treats errors as device failure. A dropped Write should return a successful consumed length appropriate to this single-packet API. OPEN must preserve normal packet semantics rather than impose the restrictive PROBE parser on all connected traffic.

## 2. WG queue retirement is a concrete requirement

Pinned Device.NewDevice starts RoutineReadFromTUN immediately, even before Up. Therefore CLOSED must exist before constructing Device, not be installed afterward. RoutineSequentialSender explicitly permits stop stragglers. Read filtering cannot recall packets already staged/encrypting/queued. Peer.Stop flushes staged/key state, but an already-running Send must still be fenced.

Required replacement order: permanently close old generation with send/write acknowledgement; stop/close old Device; wait for Device.Close/Wait completion and old TUN-reader exit; only then attach the next device to a duplicate. Never have two WG readers consume the same retained TUN queue. Do not use NativeTun.Flush as a drain: the pinned implementation is a no-op.

An interval without a consumer accumulates kernel TUN packets. Drain/drop them in CLOSED before probe/open, with bounded work and failure leaving the fence closed. A long-lived owner reader that forwards into a generation-specific virtual tun.Device is an alternative that avoids reader handoff. Distinguish packets accepted at the gate after OPEN from their original kernel enqueue time: a userspace EAGAIN drain does not prove no packet can arrive between empty-check and publication. The actual required no-precommit-send property is enforced by the send gate; do not claim a perfect packet-generation timestamp boundary from a drain alone.

The encrypted Send gate cannot re-check a plaintext socket tuple. The only safe reason to enable all protected outer sends during PROBE is that this is a fresh device whose plaintext admission has never accepted ordinary child traffic. Reopening a suspended old device breaks that argument.

## 3. Protect before first send, including rebind

The pinned Java backend calls native Up before protect and ignores protection return values. Do not preserve that ordering. Device.Up calls BindUpdate, which calls Bind.Open and may start keepalives; arbitrary later BindUpdate also replaces sockets.

Preferred minimum: a custom Bind.Open opens sockets under a per-bind lifecycle lock, obtains their actual descriptors, synchronously protects every present socket successfully through the service, and only then returns receive functions to WG/marks the socket generation usable for Send. Any failure closes both sockets, returns an error, and leaves transport CLOSED. The same path must run on every reopen. An absent protocol socket is allowed only when that family is demonstrably unsupported; a protection failure on a present socket is fatal. No stale fd number may be protected after concurrent close/reuse, and no protection receipt may apply to a later socket instance.

If using a two-stage Java/native activation instead, document equivalent exclusion against Up, keepalives, handshakes, unsolicited cookie responses and BindUpdate until protection succeeds. A one-time post-Up call is not equivalent. Explicit peer handshake initiation or a parent-only DNS probe is required to avoid waiting forever for a handshake that otherwise depends on denied child traffic.

## 4. Probe tuples need a socket lifecycle owner

An exact tuple is a useful capability only while a real exclusive socket binding is held. The existing OwnedVpnDns uses DatagramSocket(), which implicitly binds to wildcard immediately; its watchdog closes raw sockets. That code must change, not merely receive a registerTuple call near send.

For each DNS UDP/TCP and HTTPS TCP socket: create unbound, disable address/port reuse, bind to the owned Network and a concrete address from its LinkProperties, bind local port zero, obtain the actual nonzero port, then register a full family/protocol/local-address/local-port/remote-address/remote-port lease before connect or send. For TCP, registration must precede connect because SYN is traffic. IPv4-mapped IPv6 and v6-only behavior need an explicit canonical policy. Never register wildcard source addresses or lease every resolved HTTPS destination behind a source port without a real corresponding connection attempt.

An owning leased socket wrapper must perform native unregister before actual close on every path: normal use, failed connect, DNS truncation fallback, timeout watcher, cancellation, TLS failure, OkHttp disposal, and exceptions during construction. Removing a Closeable from a resource set does not revoke its tuple. Close must be idempotent, unregister linearized against Read/Write admission, and lease identity scoped to native fence/generation plus unique lease id. Clear the registry on close/retire. Do not let a stale lease removal unregister a newer lease for a reused tuple.

For OkHttp, Network.socketFactory by itself cannot supply destination-aware registration before connect. Use an explicit SocketFactory returning sockets whose connect override performs binding/registration, and close override unregisters, or another equivalently reviewed transport integration. All SocketFactory overloads must preserve the rule. TLS wrapping must retain ownership of the underlying leased socket. The readiness client should be distinct from ordinary browser clients; never add a lease to general DNS/HTTP merely because it shares a helper. Require zero remaining verification leases before ordinary publication, or explicitly close the readiness client and await its lease cleanup.

PROBE parsing must bound IP length/header offsets and TCP/UDP headers; match reverse tuples only inbound. Reject fragments, unsupported IPv6 extensions, malformed/truncated lengths and ambiguous address forms. Do not admit ICMP/port-wide DNS/HTTPS as a convenience fallback. Test exact/wrong tuple, forward/reverse direction, lease removal/port reuse, malformed packets, IPv4 options and IPv6 extension rejection. The exclusivity argument assumes ordinary unprivileged sockets, not arbitrary native code with raw-packet injection or parent-process execution authority.

## 5. Commit and hard revocation currently lack the required transaction

Current RESUME_COMMIT checks continuation/authentication/authority and then activates without holding a shared security transaction lock. Current RESUME_TRANSPORT clears deniedRetention before commit. Adding nativeOpen after the checks produces a check/revoke/open race. A gate opened by the reconnect worker or by RESUME_TRANSPORT permits precommit native UDP.

Commit must be the authenticated child RESUME_COMMIT transaction after actual bind, with current claimed PID/Binder, presentation, attempt, fence generation, authentication, operation authority and original grace all checked inside an ordering shared with hard revocation. Use a native compare-and-open against a revocation sequence, not a naked setOpen. Update continuation publication and native state as one serialized outcome; on any exception after native opening, synchronously close and invalidate it before returning failure. A delayed UI callback must carry and revalidate the same publication identity.

Session methods are synchronized, and revocation listeners run synchronously under HiddenSession's monitor with an explicit nonblocking/no-broker-lock contract. Calling a potentially blocking close-and-drain from that listener violates the existing contract and may deadlock. A workable split is: listener performs bounded native invalidate (close admission/increment revocation sequence with no waiting and no Java callback), then schedules/requests drain and child retirement outside session locks; the external hard-control acknowledgement and TUN-release path must await drain. Commit holds the shared session/owner transaction during bounded compare-and-open, with a documented lock order. Native callbacks must never reenter broker/session. Audit all hard paths: Lock, Panic, expiry, replacement, owner disposal, bind failure, service destruction and native fatal error. A Java boolean cancellation check before JNI open is not a substitute.

## 6. Owner and service death need a concrete descriptor placement decision

All TUN copies in the parent means a parent crash releases the route while :hidden_vpn_browser survives. A death-recipient that kills the child after noticing parent death cannot repair that preceding interval.

**Minimum plausible placement retaining current broker process split:** send a lifetime-only TUN duplicate to the hidden child before constructing/activating WebViews or admitting any sensitive native traffic. Keep it in a dedicated holder that never reads/writes/forwards and never closes it from Activity.onDestroy, normal cleanup, parent Binder-death callbacks or revocation callbacks while that process can still send. Parent still owns the original and WG duplicates. On parent death, WG sockets disappear but the child's held reference retains the kernel TUN while the child hard-retires. Parent service onDestroy closes admission first and retains its original until child death is confirmed. Normal child return likewise requires confirmed death before final parent release. Process exit supplies final child-reference cleanup, not a Java finally block before killSelf.

This is feasible evidence, not an Android37 proof. The inspected AOSP Vpn.Connection.onServiceDisconnected sets mService=null without directly removing the interface, while interfaceRemoved performs network cleanup. Test exact API37 service/parent SIGKILL with child held duplicate and continuous native traffic, verify VPN Network/route continuity from before death through child death, and inspect the entire PCAP. Ensure no framework service teardown path resets the interface despite the live descriptor. The regular child code must not accidentally receive a forwarding API or close the keeper during rotation.

Co-locating the VPN service/native transport with the sensitive activity process is another defensible design if parent-owned verification and native admission IPC are reworked. It couples that service process's death to the child's death, but moving activity/transport code requires renewed review of authority placement and any Chromium helper/network processes. A separately surviving guardian alone merely moves the single-process-loss question to the guardian unless another live participant holds a lifetime duplicate. Do not present either deployment as proof against every OS-forced VPN teardown.

## 7. App-controlled C1 versus OS revocation

Public Android VpnService.onRevoke occurs after the system has deactivated the interface; the VPN guide explicitly says another interface is already routing traffic at callback time. Neither a retained descriptor, guardian, co-location nor fast child kill makes that callback a pre-deactivation firewall. App-controlled suspension/replacement/lock can be ordered to retain containment; OS deauthorization/replacement must be separately reported as a platform limitation, hard-retired immediately, and tested without claiming a gap-free guarantee. No policy change, silent always-on/lockdown activation, narrowed packet assertion or restricted-beta substitution is authorized by this review.

## Addendum: lifetime reader and temporal probe-port ownership

Requested follow-up, 2026-11-03. **The single lifetime real-TUN reader with per-generation virtual tun.Device is a viable refinement and preferable to repeatedly handing the real descriptor between WG readers.** It is compatible with the exact pinned single-packet interface. Proceed with this for native backend implementation, subject to the following contract.

### Lifetime reader / virtual-device API contract

- Fence owns the sole real-TUN read goroutine and a native duplicate, independently of all WG devices. The existing Java original and child lifetime keeper still supply the process-lifetime protection. Starting/stopping/replacing a WG Device never stops that real reader or closes the real file.
- Fence has at most one active generation target. Each target has its own bounded packet queue, event channel, closed signal, immutable generation identity and gate. Dispatch reads real TUN outside locks, classifies under the current gate, and enqueues nonblocking into the matching generation. A full queue drops/zeroes the packet; it must not block the lifetime drain. There must be no send-on-closed-channel race: target detachment/queue closure and enqueue need one defined synchronization scheme.
- Each queued packet owns its storage. Do not enqueue slices into the reusable real-reader buffer or retain WG caller buffers. Virtual Read dequeues, checks current generation and phase/lease again, copies into the provided buffer at the given offset, then disposes/zeroes its storage. Retirement races must not deliver another generation's packet. The recheck alone does not replace the outer Send barrier: closure can occur after Read returns.
- Revoke first permanently invalidates the old generation, detaches its dispatch target and closes admission; then close its virtual device, drain/dispose queued buffers and wait for WG Device.Close completion. Virtual Close unblocks Read with os.ErrClosed, closes only its own event/closed channels, and is idempotent. It never closes the real TUN. New generation activation occurs only after old WG teardown has completed.
- Virtual Write uses its own generation's plaintext Write barrier before delegating to the real TUN. An old virtual device can never write through the current generation's gate. Return semantics must match the pinned API; unsupported/dead generation drops consume the requested packet, while actual fatal lifetime-TUN errors trigger fail-closed fence retirement.
- Virtual MTU/Name can report the immutable established fence configuration. Use separate per-generation Events channels; do not expose a shared channel with competing WG consumers. Flush can be a no-op matching the current underlying NativeTun behavior, but must never be described as a queue purge.
- Prefer virtual File() returning nil if the complete pinned WG call-site audit permits it. Do not return the lifetime owner's real *os.File: that exports a way to close the invariant-bearing resource. Reviewed supplied snapshots show device code invoking Read, Write, Flush, MTU and Close, but the available snapshot set is not a complete module-wide File()/Events() audit. Complete that audit before finalizing the adapter. If an fd is genuinely required by another pinned path, provide an explicitly owned auxiliary duplicate with documented semantics, never the owner file.
- Fatal real-reader error closes all generation admission, reports failure, and retains available lifetime references until child retirement; do not recover by silently establishing a replacement VPN while the child is alive.

This removes competing real readers and the interval with no draining consumer. It does **not** prove that a packet observed after a new probe lease was registered was generated after that registration.

### Concrete delayed-packet aperture

The original exact-tuple design has a temporal ownership gap. A child can use tuple T while OPEN, release its socket, and have a packet for T remain in the TUN/kernel path. During suspension, the parent may newly bind the now-free source port and register T for a readiness probe. The lifetime reader can then encounter the old child packet while T is permitted. It is sent through the fresh WG transport as probe-authorized traffic even though the parent did not originate it. TCP acknowledgements might fail later, but the SYN/segment itself already escaped denial; UDP can carry the complete child payload.

This would not recreate the original off-WireGuard route-loss mechanism: the escaped packet would use the new WG transport. It nevertheless violates ordinary-child denial during verification/bound-before-commit and invalidates the exclusivity argument behind the repair. A real held socket proves ownership now, not ownership when every queued packet was produced. Nonblocking drain-to-empty, unregister-before-close, a fresh WG device, and continuous real-TUN draining do not by themselves remove this temporal ambiguity. Upstream producers can be delayed outside the reader's own queues.

**Minimum defensible integration contract:** reserve all future probe source socket bindings before admitting any sensitive child traffic for the fence lifetime. Reserve concrete local addresses and protocol families with reuse disabled; verify Android's actual exclusive binding behavior. Retain UDP parent sockets across transport generations and use them only for the fixed parent readiness traffic. Pre-bind a bounded pool of TCP sockets before child admission; allocate a never-used slot for each connection attempt, including DNS truncation fallback and HTTPS retry/address alternatives. Once a TCP slot is connected, failed, closed, or otherwise relinquished, burn it permanently for that fence lifetime; never register its tuple again, even if the OS later gives a newly created socket the same source port. A reserved-but-unused slot must remain bound and open until use or full fence retirement. On pool exhaustion, remain CLOSED and require controlled retirement/reinitialization after child death; do not silently fall back to fresh ephemeral ports.

A successful bind must reflect exclusive ownership across the relevant local-address/family/protocol namespace. Include wildcard conflicts, IPv4-mapped IPv6 behavior, and auto-bound child sockets in the runtime tests; do not assume reuse defaults. Keep an ownership ledger independent of currently active leases, so removing a lease cannot make a spent TCP port eligible again. Pool size is a bounded resource choice, not permission to weaken the rule under pressure.

No pool refill is allowed while a potentially sensitive producer for that fence survives. Before reusing an established fence for a new child, the design must handle packets from the previous lifetime; simplest is confirmed old-child retirement and a genuinely fresh fence before reserving/starting the next child. Any more permissive temporal-drain proof needs evidence extending beyond the user's own TUN queue, including delayed resolver/system producers.

Required adversarial test: queue a distinctive ordinary UDP/TCP packet matching a would-be newly reserved probe tuple, release the old socket, then introduce the lease. A naive post-hoc registration must reproduce the aperture; the actual integration must prevent obtaining that future-probe port while the child was active. Also verify TCP-slot exhaustion remains denied, reservation persists across suspend/reconnect, stale virtual queues do not reach a later generation, and the normal full-capture no-fallback assertions remain unchanged.

## Addendum: VPN app scope and external approval apps

Requested follow-up before Android backend integration. **Option (a), an explicitly chosen Private Gallery-only runtime VPN scope, is the smallest defensible integration for external approval continuity.** It changes which applications the VPN protects, so the product must obtain an informed scope choice before applying it. This is an in-product privacy setting/decision, not a request for extra chat permission to implement the authorized repair.

### Why this is an actual integration conflict

WireGuardProfilePolicy.prepare currently validates that Private Gallery is not excluded, preserves the original Interface object, and only copies/modifies peer keepalive. An empty includedApplications list therefore remains device-wide except for any excluded applications. A persistent CLOSED TUN stops all captured ordinary traffic, including a separately installed approval app if that app is within the existing VPN scope. Moving Private Gallery to the background while retaining that device-wide CLOSED fence can prevent the external approval from arriving or completing. This is not solved by keeping the WebView alive.

Android documents that an allowlist containing a package routes only listed applications through the VPN; other applications use system networking. The lists must be set before establish, and changing them requires a new VPN connection. Consequently app-scope selection belongs before any sensitive child lifetime begins. Once that child is admitted, scope is immutable for that fence lifetime.

### Required product and lifecycle contract for option (a)

1. Compute the actual effective original scope, including excluded-app semantics; empty includedApplications does not mean only this app. If the original effective scope already consists solely of this installation, no scope downgrade is being introduced. Otherwise show a scope decision before replacing the current TUN or creating/admitting a Hidden child.
2. Explain the concrete result: only Private Gallery uses this VPN for the Hidden session; other apps use their normal connection and lose coverage from this VPN for that period. Identify that this changes the currently selected device-wide or multi-app profile's runtime coverage. Do not label this merely as enabling Google approvals, enhancing privacy, or maintaining device-wide protection. Clarify that all Private Gallery processes sharing its app UID are covered, rather than promising the VPN applies only to Hidden WebViews.
3. Provide a real decline/cancel choice that preserves the original scope. Declining must not be treated as consent, silently select a narrower route, or trigger a restricted-beta substitution. If the product keeps the device-wide scope, it must accurately explain that external apps inside that scope can be blocked during Hidden suspension. The user must be able to make the coverage/availability decision deliberately.
4. A remembered choice may avoid repeated prompts across routine reconnects, but it must be bound to the applicable profile/scope identity and explain its persistence. Profile edits, selection of a different profile with broader coverage, or a changed coverage decision must not inherit stale consent accidentally. A boolean unrelated to the selected profile and scope is insufficient.
5. Keep encrypted imported configuration untouched. Derive an immutable runtime config that preserves peer identity, keys, endpoint policy, DNS, addresses, MTU and full-route validation, replacing only the application-routing selection with this package as the sole allowed application. Clear original excluded/included application sets in that runtime copy; Android forbids mixing allow and deny lists. Never weaken routes, add allowBypass, or protect child/probe sockets to implement the choice. Only encrypted WG outer sockets receive protect.
6. Require confirmed absence of the old sensitive child before any establish/reconfiguration needed to enter the chosen scope. Reserve probe bindings and obtain child keeper readiness on the new fence before child activity. Never switch scope during a suspended child lifetime merely because an external approval app appears; that would reintroduce a route transition inside the continuity boundary.
7. Keep the effective scope visibly discoverable while this session owns the VPN. On session exit, retain the protective fence until confirmed child death, then restore the prior user-selected coverage if that is the promised behavior and the original ownership/profile is still current. Restoration must not overwrite a newer user-selected VPN/profile, superseding owner, OS revocation, or deliberate disconnect. A failed restore needs an accurate connection/scope status; do not silently claim device-wide coverage resumed.
8. Do not change OS always-on/lockdown policy. Existing device policy may still prevent excluded apps from using system networks; the feature must not promise external approval connectivity when the OS independently blocks it. This is distinct from the new native gate's behavior.

Suggested concise consent substance (product wording can be polished): "Use this VPN only for Private Gallery during this Hidden session? Other apps will use their normal connection and will not be protected by this VPN. This lets them stay online while Hidden browsing is paused. Your saved VPN profile will not be changed." Controls should name the action, for example "Use Private Gallery only" and "Keep current coverage". If restoring prior coverage is implemented, state exactly when it is restored; do not promise restoration before the lifecycle/ownership logic exists.

### Why option (b) is not a small safe substitution

ConnectivityManager.getConnectionOwnerUid is available to the active VpnService for TCP/UDP and can return INVALID_UID. This supports some attribution, but it returns ownership of a connection found now, not an immutable origin label attached to the historical packet being classified. An old Private Gallery packet can be delayed after its socket closes and its tuple is reused by another UID. A current-owner lookup could then misclassify that old packet as another app's permitted traffic. This is the same temporal ownership problem already identified for probe leases, now generalized to all external applications whose port lifetimes the VPN cannot pre-reserve.

System-mediated DNS introduces further unresolved attribution: allowing a system/netd UID wholesale may admit DNS generated on behalf of the blocked app, while denying unknown/system owners can break the approval app. Fragmented, non-TCP/UDP and inbound packets need their own policy. Moreover the current Send barrier sees WG ciphertext without the originating UID, so allowing external-app traffic during denial requires a stronger tagged-queue design and state model, not just a JNI UID lookup in the TUN reader. Keeping a global CLOSED send gate would still stop the approval app; opening it indiscriminately on an old device would reopen queued Private Gallery payloads.

These are concrete proof gaps. Option (b) should not be introduced as a last-minute convenience fallback if the user declines narrower scope. It would need a separate design and implementation review.

### Required validation

Before Android integration verdict, verify scope derivation for global, excluded-app, multi-allowed-app and already-app-only profiles; unchanged encrypted source profile; stale/missing/declined consent; and no TUN re-establishment while a child survives. Runtime evidence must demonstrate a separate controlled app can communicate during Private Gallery suspension after the scope choice, while the actual Private Gallery child retains all existing no-fallback/native UDP/DNS/verification/bound-before-commit assertions. Use separate external-app fixture identities so intended other-app traffic does not become a broad packet exclusion capable of hiding Private Gallery traffic. A synthetic approval fixture is not evidence of live Google approval.

## Addendum: Task3 session, continuation and native publication ordering

Read-only review of HEAD 6241b98 and the working source visible at review time. Inspected HiddenBrowserContinuation.java, HiddenSession.java, HiddenVpnBrowserBroker.kt, MainActivity presentation ownership, HiddenBrowserRuntime, and native gate/transport control surfaces. **The proposed continuation-lock consolidation is feasible and recommended, with the transaction obligations below.** No implementation or CI was performed for this addendum.

### Observed lock relationships

Every current continuation method is synchronized on the continuation object and several call synchronized HiddenSession methods. This establishes Continuation -> Session. A proposed final commit that holds Session and then calls continuation.activate establishes the reverse order and can deadlock against current(), owns(), state(), reconnect() or suspend() on another thread. Replacing only activate's synchronization is insufficient: all continuation mutable state, including stoppedAt/timeout/generation/lastObserved and termination, must use the same Session monitor. Constructor capture must also be atomic with the relevant authentication snapshot before publication; immutable endpoint/UID/PID fields may remain final.

Broker already acquires its privileged gate before invoking session predicates, registering/closing revocation registrations and performing some storage publication. HiddenSession callbacks execute while Session is held and explicitly forbid broker locks and session reentry. Preserve the order **Broker gate -> HiddenSession -> bounded native atomic operation**. Session-only continuation reads are safe if they never acquire Broker gate internally. Do not mechanically synchronize entire Binder dispatch or blocking suspend/prepare methods on Session.

Other existing locks still matter: broker registry operations and repository/private-app publication locks are separate. The new transaction must not acquire registry, storage, proxy, service-owner or native transport-owner locks while holding Session. Existing registry.find calls valid() while holding registry, creating registry -> Session; therefore new Session -> registry calls would introduce another inversion. Resolve immutable/captured ownership references before entering the final transaction, and use an atomic current-identity comparison inside it.

### Native interop contract under the Session monitor

Only immutable handle lookup plus native Publish/Invalidate is appropriate here. The handle lookup must use an atomically published immutable registry snapshot, or an equivalently safe direct stable reference; it must not take a registry/owner mutex that construction/retirement can hold while waiting for Java or I/O. The numeric handle must bind to fence lifetime, transport generation and authority incarnation without ABA reuse. Keep a native object alive until every lookup/call holding its snapshot has returned. Do not use an unprotected raw pointer whose owner can free it concurrently.

No string parsing/conversion, settings retrieval, JNI callback into Java, socket protection, device creation, peer handshake initiation, resource disposal, native drain or retirement belongs under Session. Gate Invalidate and Publish currently avoid application mutexes and I/O; that is the useful property. Their Go allocation/runtime behavior is not a hard real-time or wait-free latency guarantee, so do not describe them as such. Return a numeric status/receipt and handle failures fail-closed.

Revocation must reach every transport associated with the revoked authentication/presentation, including an in-construction replacement. Merely looking up and invalidating the previously installed handle is insufficient: a worker can complete a fresh transport afterward. Use an authority-scoped atomic revocation/attachment identity: register a candidate before it can enter PROBE, and allow attachment/PROBE/publication only while that same identity is live. A stale creator must retire its own candidate without closing a newer owner's transport. Final publication is always rejected after hard authority invalidation, even if a stale worker finishes configuration/readiness afterward.

### Safe operation sequence

**Begin/initial admission.** Outside monitors, allocate bounded resources and capture any immutable references needed for the transaction. Under Broker gate then Session, validate current owner/presentation, authentication, child identity if claimed, original authority, and live native fence identity; publish only an attempt/candidate registration, keeping ordinary admission closed. Start native creation/protection/readiness outside monitors. Registration needs a later activation check against the same authority identity before allowing PROBE. Initial child traffic also needs an explicit authorized readiness/bind publication point; do not open the new fence merely because a service or WG handle exists.

**Begin suspension.** Under Broker gate then Session, validate the exact child/owner and trusted loss event, invalidate the relevant native generation first, disable ordinary broker IO, invalidate in-flight resume attempts/prepared verification and record the original loss time/deadline once. Publish an internal suspending operation identity so reconnect cannot overtake the unacknowledged barrier. Repeated suspension preserves the first deadline; it must not extend grace or revive an obsolete attempt. Do not yet report confirmed denial. Release both monitors, cancel captured old IO resources and drain/retire the captured native generation. Reacquire Broker gate then Session to validate that the same suspension is still current, that its denial receipt matches fence/generation/sequence, and that original grace/authentication still permit retention; only then publish TEMPORARILY_SUSPENDED/denied acknowledgement. If superseded or expired, remain closed and retire appropriately. Capture resource lists under the gate if necessary, but perform close/cancel outside Session; potential blocking transport work should also be outside Broker gate.

The current onBackgroundAt synchronously revokes operation authority. With ordinary revocation separate from authentication revocation, ensure the suspension-specific retained-owner state is established before delivering that expected operation revocation. Its listener must still invalidate old native admission; it may suppress child hard retirement for this authorized suspension, not suppress transport invalidation. Hard authentication listeners must never be suppressed by deniedRetention. A caller-readable retained state must still require the completed barrier receipt.

**Begin reconnect / finish readiness.** Under Broker gate then Session, require confirmed denial and current retained ownership, check the original deadline, allocate a new attempt identity and change to RECONNECTING. session.onForeground may clear the session's background timer, but the continuation must retain its original stoppedAt/timeout throughout verification and bound-before-commit. Perform native replacement and DNS/HTTPS outside monitors. Reenter the same order to publish prepared/verified data only if attempt, authentication, authority, presentation, fence and transport generation still match. Make verification an immutable receipt belonging to that attempt; a volatile resumeVerified boolean alone cannot represent all these relationships. RESUME_TRANSPORT may return the verified binding information but must not clear deniedRetention or open native admission.

**Final authenticated child commit.** Parse/validate parcel structure and obtain needed cached resources before locking. Under Broker gate then Session, repeat the exact PID/UID/Binder/presentation/attempt checks, current auth and operation authority, actual bound Network/fence identity, fresh protected transport/verification receipt, and original grace using current elapsed time. Keep the state RECONNECTING until a bounded native compare-and-publish succeeds against the captured native revocation sequence. Then perform nonthrowing continuation/broker state assignments and issue a unique publication receipt. Clear stoppedAt only after successful publication; do not call current activate first, because it clears the original deadline and cannot safely roll back a failed native CAS. Any post-CAS failure must invalidate that exact publication before returning failure; rollback must never reopen or affect a newer generation. Queue UI work and serialize Binder results outside the monitor where practical; any deferred UI result revalidates its publication identity before uncovering/resuming.

A deadline check performed only before slow work is insufficient. Check at the commit decision using the existing elapsed-time clock and >= expiry semantics. If Java/native handoff can intentionally pause after that check, either carry the deadline into native Publish using the same boot-time basis and check there, or define the final bounded Java check/native CAS together as the tested publication boundary. Do not reset/rebase grace to the reconnect start. A deterministic test should pause immediately before the final publication, advance past the original deadline, and require closure.

**Hard revoke / replacement / lock / Panic.** At the revocation decision, atomically mark the relevant authority revoked and invoke native Invalidate synchronously before reporting the control action completed. Under a Session callback, set only preallocated/atomic state, invalidate, signal the known child if allowed by the current contract, and enqueue bounded cleanup; do not call continuation helpers from the callback even after lock consolidation, because the no-reentry rule and recursively firing expiry checks still apply. Perform Drain/retire/IO close outside both monitors. Any user-visible denial receipt, teardown acknowledgement or final TUN release must await the required drain and child-death proof. HiddenSession.lock itself need not block on drain while holding Session; its caller can obtain a separate completion receipt outside it. In-flight native sends already admitted before invalidate remain part of the explicit drain obligation.

### Owner replacement remains a separate atomicity obligation

MainActivity currently exposes owner and presentation generation through volatile fields, while route/destination selection and owner replacement are not all under Broker gate or Session. Calling continuationOwnerCurrent() under Session does not freeze those other fields. Another thread can change the presentation immediately after the predicate check and before native Publish. Therefore all owner-disposal/replacement paths must invalidate the old authority's native publication identity before making the replacement effective, or update a shared owner-incarnation CAS that native publication also checks. One read of a volatile owner is not a transaction. Preserve exact-owner checks for stale callbacks; never let an old owner's cleanup resolve "current transport" and invalidate or release a new owner's resources accidentally.

### Specific pitfalls to reject during implementation review

- Leaving any continuation intrinsic synchronized method or external synchronized(continuation) use while introducing Session -> continuation calls.
- Calling current()/state()/owns() from a revocation listener: these are potentially mutating expiry operations, not harmless getters.
- Calling native Close/Drain/Replace/Protect under Session, or making native Publish/Invalidate resolve a handle under the native owner lock.
- Closing lease sockets/proxies under Session, where close can wait for a worker that needs Session to observe cancellation.
- Clearing stoppedAt in activate before native CAS, or resetting grace in onForeground/reconnect.
- Returning a bind or verified receipt and clearing deniedRetention before final child commit.
- Using boolean cancellation alone to cover the native candidate creation race.
- Treating Session's swallowed callback exceptions as successful native revocation. Register/preflight a working callback before allowing admission, and retain a fail-closed authority latch whose state is checked by Publish; do not depend on an exception-prone callback as the only revocation record.
- Posting onResumed/uncover without matching the final publication receipt, especially after lock or replacement.

Required deterministic host/JVM interleavings: current versus commit (no monitor cycle); revoke versus candidate attach; revoke before/after Publish CAS; suspension drain versus new reconnect; duplicate/late suspension; native Publish failure preserving original deadline; boundary expiry immediately before commit; owner replacement after predicate check; stale cleanup after a new generation; and deliberately blocked Send/Write proving callbacks remain nonblocking while acknowledgements await drain. These supplement, not replace, the API37 packet assertions.
