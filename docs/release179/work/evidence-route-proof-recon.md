# Actual EvidenceRoute VPN/Tor proof reconnaissance

Read-only source reconnaissance, 2026-10-31. This document is the only change from this task; no suite, build, fixture, CI, git mutation or network connection was run. This is a proposed proof design, not runtime evidence. Read alongside `ci-signing-recon.md`.

## Findings that affect the implementation

* `EvidenceNetwork179Test.Https.route()` reflects the private six-argument `RouteClient` constructor and replaces DNS/socket routing with localhost or a synthetic proxy. It tests the actual HTTP primitive's cancellation/retry/bounds, but does **not** call `EvidenceNetwork.ownedVpn`, `EvidenceNetwork.tor`, or establish either Android-owned route. `EvidenceRouteCoordinator179Test` presently covers only rejected/retired startup.
* The real entry is `EvidenceRouteCoordinator.connect("VPN"/"Tor")`. VPN pins the single owned `Network`, runs `HiddenHttpTransport.vpn(...).verifyReady()` against `https://example.com/`, then returns `EvidenceNetwork.ownedVpn`. Tor starts the actual deny-all isolation VPN, packaged Tor and private Unix SOCKS endpoint, then returns `EvidenceNetwork.tor`. Reuse this entry, rather than reconstructing a synthetic `RouteClient`.
* VPN fixture infrastructure already suffices for actual HTTPS/DNS routing: `pg1762`, peer `10.91.0.2`, DNS `10.91.0.1`, origin `203.0.113.10`, underlay WireGuard endpoint `203.0.113.11:51820`; firewall rejects origin packets outside `pg1762`. `*.fixture.invalid` resolves only through the controlled DNS. The reproducible CA in `create_hidden_vpn_fixture_tls1762.py` matches debug `raw/hidden_vpn_fixture_ca`; its leaf SANs are `fixture.invalid` and `*.fixture.invalid`. No production trust change is needed for VPN.
* Both existing origin handlers require `Content-Length`. `EvidenceNetwork`'s streaming `RequestBody` does not implement `contentLength()`, so OkHttp sends chunked POST. Neither current handler can receive an actual EvidenceRoute request as written. Add strict bounded chunk decoding for the new179 endpoints; changing the real request to a fixed-body test double would hide this incompatibility.
* The existing real onion fixture exposes only virtual HTTP port80. EvidenceRoute requires HTTPS POST. Add TLS on virtual443, an exact generated-onion SAN certificate, and a fresh independent HTTPS fixture readiness check. Do not weaken EvidenceRoute's HTTPS requirement.
* The178 validators are browser-specific: they require JavaScript/worker/WebSocket/form/multipart/STUN/download/cookie events and three1762 result JSONs. They cannot validate a focused179 route selection unchanged. Their packet checks and narrowly bounded host-adb mDNS classifier are reusable ideas; their PASS output is not reusable179 evidence.

## New fail-closed validator and evidence contract

Add `scripts/verify_evidence179_routes.py` taking `--android-results`, `--vpn-root`, `--onion-root`, `--results-root`, `--source-sha` and expected cases manifest. It must fail before any final gate on missing/extra/duplicate/skipped/failed test identities, absent outputs or mismatch. XML identity validation may call the exact179 case validator but must not rely on a self-declared success boolean.

Each method writes its unique `evidence179-route-<case>.json` into instrumentation `additionalTestOutputDir`. Fields bind case/method identity, nonce, mode, owner, route identity, pinned network handle/UID/interface, ordered operation/observation IDs, exact expected POST body/response digests, actual cancellation/revocation/loss/death result, post-retirement rejection, process-binding-null, relevant sink counter deltas, private Unix UID/mode/type checks and cleanup/credential retention. Persist route endpoints only as private-path-relative diagnostics; no relay/proxy password. Runner requires exactly one output per case, copies them with original XML and writes source-sha separately. All markers must cross-reference actual host events; JSON flags alone are insufficient.

Validator requirements:

1. VPN per nonce: exactly one accepted HTTPS POST for each submitted phase, expected method/path/body hash/length, correct response, source exclusively `10.91.0.2`; each slow start has later close. Fresh phase hostname A/AAAA DNS must be observed at controlled DNS from that same peer. No cookie/auth reuse. Denied retired phase has no POST or DNS observation. A POST submitted only once must never appear twice (retry/fallback detection).
2. Packet proof: parse original `traffic.pcap` or its captured `tcpdump -tttt -nn -vv -X` rendering, require nonempty timely capture, positive WireGuard handshake counters, correct firewall admission and actual pg1762 HTTPS/DNS records. Every fixture-origin packet and fixture DNS record must be on `pg1762`, except the existing **exactly bounded** `host_fixture_adb_multicast` exemption if needed; never blanket-exclude host/lo/UDP. Reject synthetic origin traffic on another interface even if firewall rejected it. Check recorded Network-loss occurred after receipt, not before call admission.
3. Tor per nonce: independent exact-byte **HTTPS** readiness, exact generated host and leaf SAN/CA identity, unique actual HTTPS POST/body hash at the controlled onion TLS backend, slow-start/slow-close pairs for cancellation/revocation/death, no accepted retired-phase POST. Correlate private Unix endpoint/packaged-process/sink observations from the exact tests. Reject any external DNS containing the onion hostname; within recorded Tor phase windows, reject179 sink fixture DNS queries, escaped IPv4/IPv6 sink markers, or direct fixture-origin packets. Require explicit host phase barriers so prior VPN fixture traffic cannot be confused with Tor traffic. Require positive sink counter deltas as well as negative host capture. A public Tor relay TCP connection is expected and must not be mistaken for origin fallback.
4. Bind all Android outputs, original source SHA, case manifest hash, script hashes, pcap/event hashes, fixture public cert fingerprints/SANs, health readiness and XML test identities into `app/build/evidence179/route-proof.json`. Emit PASS only if all required observations exist; absent proof remains PENDING/failed, never auto-skipped. This establishes controlled-route assertions, not arbitrary absence of all possible network traffic or physical-device acceptance.

`scripts/run_evidence179.sh` from the CI recon should pass the179 fixture args, run only explicit179 selection, copy results, preserve raw capture/events/certs, render packets after flushing/stopping capture, and invoke this validator. Capture must be closed/flushed **before** validation; preserve final `slow-closed` events before copying. After service shutdown, copy onion files before existing `ci_onion_probe.py --stop` removes temporary root. Always-cleanup must still archive diagnostics on failure. Only then can overall `final-gates.json` set owned_vpn/native_tor/dns_and_packet_observation/revocation PASS with original exit0. The existing178 runner and historic production evidence remain unchanged.

No new workflow file, real owner VPN profile, paid API call, release TLS override, production endpoint override, browser suite or claimed passing run is needed for this implementation.
