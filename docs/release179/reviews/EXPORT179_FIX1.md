## F1 — Important: valid near-limit local v1 catalog becomes unreadable

`EvidenceCodec.java:39–41` accepts v1 input, then constructs `EvidenceCatalog`. `EvidenceCatalog.java:63` adds live-source mappings and line70 immediately re-encodes the entire object with codec v2 under the unchanged 4MiB quota. The added fields can push a valid existing v1 catalog over that quota **during read**, causing `Invalid evidence catalog` with cause `Encoded evidence quota exceeded`. The existing ciphertext is not overwritten, but its annotations become inaccessible. The report's statement that migration remains subject to the quota does not satisfy required local-v1 readability/preservation.

Confirmed using one new isolated host probe, not a passing-suite rerun: 64 valid records, each with a 65,000-character note, plus one analysis selecting all 64 with valid lineage. Its independently written v1 encoding is **4,188,265 bytes**, below **4,194,304**. Compiling the pre-fix Catalog/Codec reconstructed from this scoped diff and decoding that fixture succeeds (`decoded`). Compiling the frozen fix1 Catalog/Codec and decoding the identical fixture fails with the two exceptions above. No Android execution is involved.

Required: provide a bounded, non-destructive path that can still read valid existing v1 catalogs when eager v2 expansion exceeds storage capacity. Do not silently discard notes, audit, lineage, accepted JSON or reference authority, and do not claim an oversized v2 rewrite fits the existing encrypted-store limit. Add a near-limit v1 regression for both owners that proves readable content is preserved and any unsupported size-growing write fails without replacing the original ciphertext. The small migration fixtures in `EvidenceHistory179HostTest` do not exercise this edge.

Probe source: `/tmp/ExportMigrationQuotaProbe.java`; isolated compilation directories: `/tmp/export179-v1-probe/classes` and `/tmp/export179-fix1-probe/classes`.
