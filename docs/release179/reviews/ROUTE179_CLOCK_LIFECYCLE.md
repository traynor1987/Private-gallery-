## Important findings

### I1 — The UiAutomation command is a shell script passed to an API that does not invoke a shell

`EvidenceRouteClockLifecycle179.kt:53–55` constructs a string beginning with `'timeout' '3' 'am' 'broadcast'`, followed by redirection, a semicolon, shell variable assignment and `printf`, and passes that whole string directly to `UiAutomation.executeShellCommand`.

The AOSP implementation of [UiAutomationConnection.executeShellCommandWithStderr](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/UiAutomationConnection.java) calls `Runtime.getRuntime().exec(command)`. Android's [Runtime.exec(String)](https://android.googlesource.com/platform/libcore/+/master/ojluni/src/main/java/java/lang/Runtime.java) tokenizes on whitespace; it does not remove shell quotes or evaluate shell syntax. Consequently the executable token includes the literal single quotes around `timeout`. The command cannot launch the intended program on a normal device. Even merely removing those quotes would leave `2>&1`, `;`, the assignment and `printf` as arguments instead of producing merged output and the required status trailer.

The first `STATE` at line 69 therefore cannot produce the required raw frame. This is a deterministic invocation-contract defect, before any duplicate/cancellation/timeout behavior is exercised. The synthetic host fixtures manufacture the expected shell output and cannot detect it. The report's statement that this implementation uses actual shell ordered broadcasts describes intent, not an executable command path.

**Minimal correction:** use an explicit, correctly transported shell script through a supported UiAutomation API, or a direct command path with separately captured status/stderr. Preserve bounded execution, exact recorded argv/script correspondence, unmodified raw bytes, real package/user-scoped delivery and fail-closed status parsing. Do not simply prepend `sh -c` around a whitespace-containing quoted script: the same `Runtime.exec(String)` tokenization must be accounted for. Add a narrow command-construction/API-contract regression; actual API37 delivery remains required.

### I2 — The competing-sample control waits for a duplicate that the ordered-broadcast queue cannot deliver before the first result finishes

`EvidenceRouteClockLifecycle179.kt:81–86` starts two requests, awaits the first claim, then waits for poison before closing. No sample is read and no first pending result is completed in that interval. Lines 137–142 and the decoder's `POISON` table require the first poison to be `Rejected clock command: java.lang.IllegalStateException` from the duplicate.

The modern AOSP [BroadcastProcessQueue](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/BroadcastProcessQueue.java) has one active broadcast per target process. [BroadcastQueueModernImpl.dispatchReceivers and scheduleReceiverWarmLocked](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/BroadcastQueueModernImpl.java) retain a blocking delivery until `finishReceiver`; [BroadcastRecord.isAssumedDelivered](https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/am/BroadcastRecord.java) does not assume completion for an ordered broadcast. These are not merely serialized `onReceive` method bodies: `goAsync()` keeps the first ordered delivery active until its PendingResult is finished.

After I1 is corrected, both shell request intervals may overlap, but the second target callback remains queued. The first claim's one-second handler deadline (`EvidenceRouteClock179.kt:120`) therefore supplies `Clock sample deadline expired` before the queued duplicate can run. `bad()` preserves that first reason. The strict expected duplicate-poison check subsequently fails; if close unregisters before the second dispatch, the second result can also fail the required inventory. Overlap alone does not establish the claimed duplicate transition. This first mandatory scenario prevents the remaining seven and the real positive route from completing.

**Minimal correction:** redesign this single one-shot control around actual ordered-delivery serialization. Establish a reachable duplicate/consumed-request transition with real broadcasts, record the first completion and second rejection truthfully, and adjust the exact receipt/decoder expectations accordingly. Keep exactly-one acceptance/finish, rejection of later reads and final success after poison, and the separation from the six positive route samples. Do not substitute a direct receiver call or relabel deadline poison as proof that the duplicate guard executed. The report must distinguish overlapping submissions, serialized delivery through pending completion, and any actual read/deadline race.
