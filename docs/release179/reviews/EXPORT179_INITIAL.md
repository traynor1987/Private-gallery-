## E1 — Important: retained incident analysis is silently omitted after unlink

`app/src/main/java/uk/co/traynor/privategallery/core/evidence/EvidenceArchive.kt:34-41` requires every analysis `evidenceId` to be in the currently attached/exported record IDs. For analysis A+B applied to an incident with retained lineage A+B, unlinking B while leaving its library record intact leaves analysis IDs A+B but export IDs only A. The analysis is excluded, despite its complete lineage being selected and policy-checked. The report loses the advisory body/receipt and structured export loses the accepted JSON. B's fingerprint alone is retained. This is the known uncompleted edge, confirmed in the recovered implementation.

The current catalog-based export representation is also an obstacle: simply removing that filter makes `EvidenceCatalog` reject an analysis referencing B when B is absent from the selected records (`EvidenceCatalog.java:63`). Adding B's record would silently include its original and unrelated live notes, violating the binding brief. An export-specific representation/reference mechanism or another explicitly reviewed projection is needed that preserves relevant advisory/source references without expanding original or annotation selection. Keep all retained contributors subject to live owner/identity/VaultOnly checks. Update the exclusion wording in `EXPORT179.md:30` to distinguish genuinely unrelated analyses from retained contributors of selected incidents.

Required regression: A+B analysis with real suggestion/event references, separately applied to incident A+B; unlink B but keep B's live record and distinctive unrelated notes. Export only that incident in encrypted and confirmed-plaintext modes. Assert advisory JSON/receipt/readable summary and A+B fingerprints are present; B is labelled unattached; B original/notes are absent; encrypted open and re-export succeed. Restrict/change/remove B's live original and assert both export modes fail before output admission. The existing `advisoryAiAndUnattachedRetainedLineageStayLabelledWithoutReattachingOriginals` test removes the only record from the catalog and uses empty suggestion/event arrays, so it does not cover this case.

## E2 — Important: valid metadata ordering can make the writer reject its own archive

`EvidenceArchive.kt:56` serializes `metadata.embedded()` in its existing map order. `EvidenceCatalog.Metadata` preserves insertion order (`EvidenceCatalog.java:13`), while the authoritative binary encoder explicitly sorts these keys with `TreeMap` and decoding preserves that sorted order (`EvidenceCodec.java:50-51`). `EvidenceArchive.decodeMetadata` then regenerates JSON from the decoded catalog and requires exact byte equality (`EvidenceArchive.kt:81-83`). A valid metadata map inserted as `z -> value, a -> value` therefore produces an export that fails open as `Noncanonical evidence schema`. The independently regenerated transcript also iterates the embedded map (`EvidencePdf.kt:33`, `EvidenceOpenedArchive.kt:80-82`), so fixing only the JSON serialization leaves a second ordering mismatch.

Define one deterministic ordering for both readable metadata and transcript/PDF projections before writing and regeneration. Do not weaken exact-schema rejection to accept unknown/conflicting claims. Required regression: two or more embedded keys deliberately inserted in reverse lexical order; perform write → authenticated open → confirmed plaintext re-export for both owners and compare source metadata/original bytes. Include a catalog encode/decode boundary and confirm the same projections on either side. Existing archive fixtures contain only one embedded key.

## E3 — Important: retained structured AI references can make an incident unexportable after record removal

`EvidencePdf.kt:43` unconditionally calls `EvidenceAi.details(a)`. Reference-only catalog removal intentionally retains the accepted analysis text and lineage but removes its live `evidenceIds` (`EvidenceCatalog.java:83-86`). `EvidenceAi.details` validates all raw suggestion/event references against only those remaining IDs (`EvidenceAi.kt:299-301`, `readStructure.ids`). Therefore a previously valid accepted analysis with a suggestion/event citing a subsequently removed record now throws during report construction. The selector can retain that analysis through selected incident lineage, making both encrypted and plaintext export fail for otherwise permitted retained incident content. The current removed-reference test avoids the defect through empty suggestions/events.

Provide a safe historical-reference interpretation for export, retaining the original accepted JSON and explicitly identifying absent/unattached references through validated provenance. Do not silently discard structured fields, treat arbitrary raw IDs as trusted, or reattach the removed record/original. Coordinate any required model/AI contract extension with those owners. Required regression: valid applied analysis with a nonempty suggestion and event; remove a contributing library record; export the retained incident, open it, and assert the advisory remains readable, its historical references/fingerprints remain labelled, no removed original is attached, and unrelated/restricted lineage never bypasses policy. Include a genuinely foreign raw reference rejection case.

## E5 — Minor: growable plaintext buffers abandon unwiped previous allocations

`EvidenceOpenedArchive.kt:89-91` and `EvidencePdf.kt:78-81` subclass `ByteArrayOutputStream`, use its automatic growth, and wipe only the final `buf`. Each growth copies plaintext into a replacement and leaves the previous owned array unwiped until garbage collection. This undermines the intended owned-buffer hygiene on successful open/close and cancellation, although it does not create a plaintext disk file or demonstrate an external disclosure. `EvidenceCodec.Buffer` already shows a bounded growth approach that wipes replaced arrays.

Use an equivalently bounded/wiping growth implementation for these report/metadata buffers (without allocating the full quota unnecessarily). Test forced growth and failure cleanup through inspectable test hooks/helper ownership, including the returned-copy lifetime. Immutable JSON/report strings remain a separate managed-runtime limitation; do not promise universal heap erasure.

## Security properties supported by source inspection

- Writer selection binds catalog digest and owner, rejects empty/duplicate/invalid selection through Egress, and checks direct plus retained source policies before admission, around verified original reads and before successful completion. Original bytes stream through a fixed buffer, actual size/SHA-256 are compared, and the reader's authenticated EOF must complete before success. No original delete/import mutation exists in this scope.
- Header parsing fixes version/scrypt parameters before KDF allocation; password encoding is strict UTF-8 without trimming. Salt/nonce are random on write, all 52 header bytes are GCM AAD, and lightweight BouncyCastle streaming avoids whole-container JCE buffering.
- Open copies only ciphertext once to an exclusive private stage, changes its permissions and retains one descriptor. The complete first decrypt/tag check precedes ZIP parsing; the second pass drains the strict ZIP grammar to authenticated EOF before metadata/report return. Expected owner, exact schema, declared source policies, all originals, document hashes and transcript are checked before publication. No plaintext original is written to disk.
- The ZIP parser bounds expanded bytes/entry counts, validates local/central-directory agreement, CRCs, duplicate names, traversal, unsupported compression, special files and trailing data. It does not hand raw entry paths to a filesystem.
- Opened plaintext re-export requires explicit true and fresh current authority, performs a full authentication-discard pass before output, then streams the original ZIP from the held ciphertext. Failure can leave caller-owned partial output; successful receipt is gated after streaming. Close revokes subsequent access immediately and wipes held arrays/key once any synchronized borrow/write finishes. Root must keep its already documented asynchronous close/provider cancellation handling; this review does not certify that integration.

These are source-level observations, not runtime or release approval. Original-stream memory is bounded independently of original size; PDF's native page accumulation and peak allocations still need the pending platform stress/cancellation verification. No remediation was applied in this review.
