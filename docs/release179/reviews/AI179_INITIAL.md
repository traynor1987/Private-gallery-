## Findings

### AI179-R1 — High: depth precheck and Android JSON parser accept different grammars

Locations: `EvidenceAi.kt:247–248`, `:279–280`, `:309–316` (exception handling `:274`).

`requireJsonDepth` recognizes double-quoted strings but not comments or single-quoted strings. Android `JSONObject`/`JSONArray` use a lenient JSONTokener that skips comments, accepts single quotes and recursively parses arrays. A quote inside a comment therefore changes the precheck's quote state while leaving the real parser's state unchanged. The check does not enforce the promised parser nesting bound.

Concrete model-output string, where repetition describes the generated bytes:

```text
{"ignored":/*"*/ + "[" repeated 12000 + "0" + "]" repeated 12000 + /*"*/}
```

The new source-level probe constructed that 24,023-character string and observed `scanner_accepts=True`, `scanner_maximum_depth=1`, versus 12,000 actual array levels. It fits both the response limit and the output-text limit. A provider can return it as a normal JSON-escaped `output_text`; `validateStructured` then hands it to Android's recursive parser before its own walk-depth check. Stack exhaustion can escape both `catch(Exception)` handlers as `StackOverflowError`, rather than becoming the fixed sanitized failure. The exact device failure threshold has **not** been measured.

Dependency evidence: [AOSP JSONTokener](https://android.googlesource.com/platform/libcore/+/master/json/src/main/java/org/json/JSONTokener.java), `nextValue`, `nextCleanInternal`, and `readArray` (reviewed 2026-10-31). These establish the lenient grammar and recursion; Android37 execution is still required.

Required correction: use a strict bounded parser, or validate the complete strict JSON grammar and nesting before invoking the lenient parser. Merely catching stack exhaustion or adding a post-parse depth walk does not establish a bounded parser. Apply the same protection to the outer Responses document and structured output text. Add adversarial cases for comments containing quotes, single quotes, malformed/trailing input, and deeply nested output text; assert a sanitized rejection without stack exhaustion or publication.

### AI179-R2 — Medium: Markdown-fenced structured suggestions bypass selected-ID validation

Location: `EvidenceAi.kt:258–261`, `:276–280`; existing test `EvidenceAi179Test.kt:122–128`.

`validateStructured` returns immediately unless the text, after leading whitespace, begins with `{` or `[`. A very ordinary model response beginning with a Markdown code fence, or prose followed by a JSON block, skips all reference checks. For example a fenced JSON object containing `suggestions:[{kind:"GROUP",evidence_ids:["foreign"],title:"x",reasons:["x"]}]` is appended to the accepted Analysis even though the equivalent bare object is rejected. Local `Analysis.evidenceIds` and lineage remain selected-only and no automatic apply occurs, which limits the impact, but the advertised contract that structured suggestions reference only selected originals is not met.

Required correction: define an unambiguous structured response contract, normalize only explicitly supported wrappers and validate their entire contents, or fail closed on structured wrappers instead of silently treating them as unchecked prose. Do not infer authorization from free text. Add bare/fenced/prefaced/array/multiple-block cases and verify foreign references cannot enter accepted structured suggestions; valid selected references must still work.

### AI179-R3 — Medium: separate owner backends can race creation of the shared Keystore alias

Location: `EvidenceCredentials.kt:95–104`, with dependency `core/editor/AiCredentialStore.kt:48–56`; existing test `EvidenceCredentials179Test.kt:25–31` is sequential.

Each credential accessor creates an independent `AiCredentialStore`, and the new shared operation gate is scoped to path **and owner**. The reused store's `key()` is synchronized only on its own instance, although every instance uses the same global AndroidKeyStore alias `private-gallery-ai-provider-v1`. On a fresh installation, concurrent first setup/read operations through two owner backends (or another existing AI adapter) can both observe the alias absent and both generate it. There is no process-wide alias initialization fence. Replacement/failure during that race can leave a newly written owner's ciphertext undecryptable; different provider IDs/AAD do not prevent this key-initialization race.

This is a dependency integration finding, not a claim that a race was reproduced on a device. The new same-owner generation lock correctly addresses a different race and does not cover this shared alias.

Required correction: coordinate alias lookup/creation process-wide across all consumers of that alias, retaining the per-owner operation/generation gates for credential removal. A change to the reused store requires its owning reviewer to coordinate scope; serializing only one EvidenceCredentials instance is insufficient. Add an isolated, disposable-alias first-use concurrency test across two store instances/owners and verify both credentials remain decryptable. Do not delete/reset the real shared application alias as test setup. Also exercise concurrent same-owner setup/remove/acquire with barriers, rather than relying on the current sequential removal assertion.

## Source-level assessment outside the findings

- Prepare performs no request/key acquisition, defaults to text-only, bounds explicit images, reencodes fresh JPEGs and retains exact body bytes. Each selected original is read to EOF with size/hash checks; image publication follows reader return. Direct selected fields are used, so unrelated retained incident content is not implicitly included. Policy checks use AI egress.
- Consent binds catalogue digest/revision, owner, selected IDs/images, task/model, route identity, body digest and pricing revision. Claim is one-shot and precedes key acquisition. Digest/source/route checks bracket the network call. Correct current-catalogue callbacks and explicit confirmation remain caller obligations outside this scope.
- Credential IDs/AAD are owner-specific, mutable owned copies are wiped, active send keys have generation validity and removal callbacks. Provider errors and normal parser/network exceptions use fixed local messages; decoded direct key echoes are rejected. Java/HTTP strings are not erasable, as the handback acknowledges.
- Routes explicitly disable redirects, cookies, cache, connection retry and origin authentication follow-ups; POST bodies are one-shot. Admission and close share a monitor; retirement cancels admitted calls before closing the bridge. VPN pins sockets and OwnedVpnDns to the verified owned Network. Tor uses the private Unix/TOR_ONLY bridge, authenticated numeric loopback and prohibited origin DNS. These are inspected code paths, not packet evidence.
