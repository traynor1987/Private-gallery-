## Security and mathematical assessment

Let `T` be the host-clock coordinate at which the actual Android action counter is read. Provided the accepted request is fresh and its ordered-broadcast completion is emitted only after that exact read, `Hs <= T <= Hr`. Therefore the mandatory `C >= Hr + 5 ms` establishes conservative host observation ordering independently of a host/device rate estimate. The additional intersection with the original arm interval is a fail-closed consistency check. It cannot weaken the final guard: `min(I_arm.high, I_probe.high) <= I_probe.high`, so the final probe check dominates the intersection's upper-bound check. This remains safe even if the extrapolated arm interval's implicit equal-rate model is imperfect. Retain both the nonempty-intersection requirement and the independent probe-upper guard; do not later optimize away the latter.

The design correctly retains the limited claim: the genuine first host EOF/reset/broken-pipe observation follows the immediately-pre-invocation action timestamp in the controlled fixture. It does not prove kernel FIN arrival time or counterfactual causation against an independently closing peer. The final local liveness/publication assertions, genuine worker failure after action, original continuously active peer reader, actual first EOF timestamps, unchanged failure limits and unchanged endpoint remain essential. A close between the action and the completed ADB reply may honestly fail this stronger proof. The 100 ms bracket limit is a maximum uncertainty budget, not a guarantee of success or authority to delay EOF reads/retry the application.

The same-read rendezvous avoids `/proc/uptime` equivalence, extrapolation/sample-age estimates, midpoint calibration and a new drift assumption. The design preserves six exact destructive phase samples: VPN cancel/revoke, VPN loss, Tor cancel/revoke, Tor death. VPN loss still makes no remote-close claim. Missing, disjoint, foreign, duplicate, stale, wide or malformed calibration fails. No new case, bypass, production service, network endpoint, workflow or version change is proposed.

## Receiver, process and cancellation assessment

The dynamically registered receiver is an appropriate way to share the instrumentation process's pending state. A manifest receiver in an assumed separate test process would not be an equivalent implementation. A target-context registration, exported flag, sender-side DUMP permission requirement, random action/run nonce and exact phase/arm identity are consistent with this design. Host serial/transport metadata must remain independently observed; a value merely echoed from an instrumentation argument is not Android hardware identity.

The documented Android APIs support the proposed mechanism: `registerReceiver` accepts the sender permission and dispatch handler; `goAsync` returns a `PendingResult`; that result can be completed off the receiver thread; `elapsedRealtimeNanos` is the actual supported counter. AOSP's shell broadcast command uses ordered delivery and, unless asynchronous mode is requested, waits for the completion result. An exit status of zero alone is insufficient, which the proposed result-code/payload checks correctly recognize. Do not use `--async` or treat `--receiver-permission` as a substitute for the registration's sender permission.

The no-main-blocking, one-shot claim, immutable sample and separate action ownership requirements are sound. Implementation review must inspect the concrete terminal states: timeout/cancellation cannot later publish a successful sample, duplicates poison the case even after an earlier successful reply, and `actionTimestamp` cannot run for an expired/poisoned claim. Pending results need one finisher, and all shutdown paths need to release them, unregister, stop/join the owned thread/helper and preserve the original failure status. The proposed cancellation/race/cleanup controls are necessary evidence, not optional test coverage. Receipt success must only be finalized after these lifecycle checks; no successful payload may mask a later recorded poison/helper error.

## Raw evidence and remaining contracts

The source/nonce/phase/token/process/boot bindings and byte-for-byte Android/host payload agreement are sufficient design constraints for freshness and attribution. Implementation must use the existing selected transport throughout, reject a replacement process/boot, and retain raw command framing, stdout/stderr, statuses and every attempt. Boot identity must be read independently, not synthesized from elapsed time or trusted solely because two echoed strings agree.

The archive and replay plan is acceptable: exactly six required phase observations plus lifecycle/identity records, required helper status, source files and raw evidence are hash-bound; the same frozen CLI independently recomputes the proof. Merely hashing whichever files happen to remain is not enough: its required-evidence inventory must make deletion fail, as the design's mutation controls demand. No trusted helper PASS, optional legacy path, synthetic proof artifact or stale route-proof reuse is permitted. Existing 153-case/no-skip checks, original statuses, DNS/pcap/no-fallback gates, owned VPN/packaged Tor/private Unix ownership and host-window/drain separation remain mandatory.

The classname correction is appropriately explicit and retains exact validator identity. The firewall change is a strict representation repair: accept only `all` or `0` in the exact all-protocol REJECT row while preserving the full raw observation. The proposed whole-chain parsing and rejection of extra rows, protocol6/17, missing negation, wrong interface/source/origin, ACCEPT and malformed output prevent a substring-based broadening of the rule.

## Findings and minimal clarifications

**Critical: none. Important: none.**

1. **Minor — spell out boot identity acquisition and delivery targeting.** The design requires an independently read boot ID but leaves its concrete mechanism implicit. Name the exact read (for example, bounded strict UUID parsing of `/proc/sys/kernel/random/boot_id` independently in the target process and selected ADB transport), record read status, and fail if API37 policy denies it. Do not silently adopt broader privileges or substitute an argument echo. Bind the explicit Android user and package-scoped registered-receiver delivery to the same target invocation. Existing AOSP policy demonstrates a basis for proc-random read access, but it does not substitute for actual access on the selected API37 image. This is a concrete implementation detail, not authority to add a manifest component.

2. **Minor — make the single-finisher and unconditional teardown wording explicit.** Android documents `PendingResult` as not thread-safe. Assign its result-setting/`finish()` to one owner; timeout, sample completion and cleanup must converge on that owner or an equivalent race-free one-shot transition. Never block its HandlerThread waiting for work scheduled to the same thread. Place receiver/helper teardown so a preceding route-cleanup exception or coroutine cancellation cannot skip it. Keep serialization/hashing off the critical action-read-to-invocation path where practical; only the bounded immutable publication/signal belongs there. These are the concrete realization of the existing no-wait and finally requirements, with no new protocol required.

3. **Minor — qualify the suspend/rounding statements.** The design says a suspended sample necessarily widens the host bracket. Linux host monotonic time may exclude host suspend; ordering remains sound because the final comparison is in the same monotonic domain, but that sentence is too broad. State that device/transport delays while the host clock advances widen the measured bracket; do not infer a wall-time bound from host monotonic alone. Also explicitly compare the recorded close float exactly (rational arithmetic), or floor a close converted to integer nanoseconds while rounding upper bounds upward. Never ceil `C` into passing a one-nanosecond boundary. No extra clock channel is needed to fix either wording issue.
