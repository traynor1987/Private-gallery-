# Hidden VPN interactive transport architecture investigation

Read-only investigation; production sources unchanged. Recommendation: a dedicated non-exported `HiddenVpnBrowserActivity` in `android:process=":hidden_vpn_browser"`, bound to the exact owned WireGuard `Network` **before initializing WebView**. Keep Primary and current Tor JS-off runtime in their present processes and profiles. Do not switch one running WebView process between VPN/Tor/direct routes.

## What the platform actually supports

Android `ConnectivityManager.bindProcessToNetwork(network)` pins subsequently created sockets and hostname resolution to that Network. On its disconnection those sockets and resolutions fail; passing null clears the pin. Chromium's WebView architecture says browser and Network Service run in the embedding application's process, even when renderers are sandboxed out of process. Consequently there is no demonstrated “WebView networking is in another process” blocker and no demonstrated requirement for an HTTP CONNECT bridge merely to route interactive WebView requests. This is a supported architecture inference combining those contracts; verify it on the packaged provider/device before a fail-closed claim.

References (primary sources, checked 2026-10-28):
- https://developer.android.com/reference/android/net/ConnectivityManager#bindProcessToNetwork(android.net.Network)
- https://developer.android.com/ndk/reference/group/networking (android_setprocnetwork expressly covers future native sockets and DNS)
- https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/docs/architecture.md
- https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/browser/network_service/README.md
- https://developer.android.com/reference/android/webkit/WebView#setDataDirectorySuffix(java.lang.String)

The process pin is a routing guarantee, **not a session authorization firewall**. Revoking a Hidden session while its VPN Network stays up does not itself revoke WebView sockets. Stopping views or polling every 500 ms is not an atomic transport gate. If the requirement is broker-controlled socket cancellation at session revoke without waiting for process exit, use the optional bridge below as well.

## Concrete integration

1. Main process remains sole WireGuard backend owner. Extract current `MainActivity.hiddenOwnedVpnNetwork()` into an owner service/broker returning `OwnedVpnLease(epoch, Network, peerVerified)` over Binder. Current discovery requires `ownsTunnel`, CONNECTED and exactly one TRANSPORT_VPN Network with `ownerUid == myUid`; retain these checks and fail on ambiguity. Register network callbacks (request VPN transport with default NOT_VPN capability removed), revalidate capabilities and owner generation, and revoke lease on lost/ownership/capability/state change. Do not select arbitrary default network or another VPN. A `Network` is Parcelable; no private configuration or keys need cross processes.
2. Add non-exported process activity plus Binder session-control contract. Parent issues one-use capability after Hidden unlock; bind capability to session generation, intended mode, child Binder death, and parent Binder death. Do not place vault keys or reusable session credentials in launch intents/saved state. Child bootstrap obtains lease and checks ownership, successful `bindProcessToNetwork`, and `getBoundNetworkForProcess()==lease.network` before any WebView/provider initialization. Fail without constructing WebView if any step fails.
3. Call `WebView.setDataDirectorySuffix("hidden_vpn")` before other android.webkit calls in this process (ideally process-aware Application initialization). Then retain generation-unique AndroidX profiles and explicit retirement/clear logic; distinct data-directory suffix is mandatory across processes and provides Primary cookie/storage independence. Keep DOM storage/cookies enabled only for the VPN browser profile; enable JS and ordinary networking only after gates. Remove GET interception for VPN views; preserve non-http(s) navigation denial, file/content access denial, TLS error cancellation and native permission policy. Service worker native networking must use same bound process, not the old synthetic GET interceptor.
4. Child never calls bindProcessToNetwork(null), never silently rebinds to replacement Network, never falls back to Tor/default. Any revoke/network loss/parent death closes UI and ends child process. New browsing requires new authorization and fresh process. Keeping the dead Network pin until exit protects the loss-to-exit interval. A restarted activity must bootstrap again and cannot restore page/session authority from Bundle.
5. Adapt lifecycle: `MainActivity.onStop()` currently closes `hiddenBrowserOwner`, so external child launch needs an explicit handoff ownership state. All real lock, screen-off, task-removal, mode change and owner death paths must revoke the child. `VpnOwnershipService` and `OwnedVpnTunnelRegistry` are process-local, so child must not instantiate a second backend or assume their singleton state is shared. `android:stopWithTask` and destruction callbacks alone do not guarantee cleanup after process death; Binder death and closed-by-default recreation are required.
6. Uploads: implement `onShowFileChooser` using explicitly chosen URIs and revocable bounded grants/streams. Existing callback always returns null. Hidden Vault source uploads can be supplied through a narrow, session-bound read-only content provider/pipe that checks current authority; no plaintext file or broad vault bridge. Screen-off/lock must cancel chooser and close streams. Decide deliberately whether launching picker preserves or revokes authorization.
7. Downloads: native GET downloader can reuse exact lease Network.socketFactory + Network.getAllByName and same profile cookies/headers, then stream through Binder ParcelFileDescriptor into main-process encrypted HiddenRepository. Reject stale generation before import/commit. Existing downloader is GET-only and not tied to WebView response body. See limitation below before claiming arbitrary browser downloads.

## Optional brokered proxy path

For auditable cancellation and broker-owned egress, add a session-scoped loopback HTTP forward/CONNECT proxy owned by the main transport broker. Every upstream socket and DNS lookup uses lease Network; bridge tracks and closes active duplex streams synchronously on revoke. Configure ProxyController only in child process, wait for completion callback, use one proxy rule, **no DIRECT fallback**, and remove implicit local bypasses (`removeImplicitRules`). Keep process binding as defense for bypass/non-proxied protocols; proxy-only interception is not a complete firewall (e.g. protocol coverage must be tested). Startup remains network-blocked until configuration acknowledgment. CONNECT preserves end-to-end TLS and all request bodies without MITM. Dependencies: AndroidX WebKit PROXY_OVERRIDE runtime feature, complete bounded HTTP parser/CONNECT forwarding, per-session listener/token access control and cancellation tests. Current WebKit 1.13.0 dependency already contains proxy API. Do not add bridge complexity solely on unsupported assumptions about an out-of-process WebView Network Service.

Primary references: https://developer.android.com/reference/androidx/webkit/ProxyController and https://developer.android.com/reference/androidx/webkit/ProxyConfig.Builder . Overrides are process-specific and affect every WebView in that process, so applying them to current shared MainActivity process is unsuitable.

## Demonstrated limitations / release gates

- Native WebView `DownloadListener` provides URL/user agent/content disposition/MIME/length, **not original request body or response stream** (https://developer.android.com/reference/android/webkit/DownloadListener). Reissuing a GET cannot faithfully save arbitrary POST attachment responses, one-use URLs, or blob downloads. A CONNECT tunnel cannot inspect encrypted HTTPS bodies either. If “downloads” means arbitrary browser-native response download parity, this is an actual API gap requiring a separately validated browser engine/download API or a consciously scoped alternative. Do not call GET replay full parity. Interactive POST/page rendering itself has no such interceptor problem once native WebView networking is enabled.
- Process binding does not preserve current private-address URL policy automatically for every JS/subresource/worker/socket request. If that policy must be enforced below navigation level, broker proxy target validation (including DNS rebinding and every resolved address) or another network policy layer is needed. Keep current Tor interceptor and JS-off policy separate.
- No build/runtime or physical network evidence was produced by this investigation. Live owner VPN profile, controlled upstream fixtures and packet/DNS observation remain acceptance dependencies, not reasons to assert unsupported architecture.

Required tests: exact POST bytes/form encoding/multipart and streamed uploads; fetch/XHR/cookie/redirect/worker/WebSocket paths; full native page JS and storage independence versus Primary/Tor; no duplicate POST on redirects; encrypted download integrity and explicit POST/blob coverage decision; TLS errors remain cancelled; IPv4/IPv6/DNS direct/DoH/WebRTC/provider background traffic checked with physical capture; permission revoke, Network loss/replacement, reconnect, parent/child/renderer death, screen-off, task removal and mode switches during active upload/download. Assert old generation can neither make new connection nor commit vault output; assert no direct DNS/socket succeeds after loss. Test cold and killed-process launch, picker lifecycle, and simultaneous Primary/Hidden profile separation. Do not claim network fail-closed from exit-IP pages or VPN icon alone.
